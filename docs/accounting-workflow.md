# Перестройка бухгалтерии

Изменения подготовлены локально в `/workspace/transport-crm`. На сайт не опубликованы.

## Пользовательский сценарий

1. Выбрать заказчика, объект и даты услуг. «Счёт» заполняет строки выполненных рейсов без предыдущего счёта: услуга, объём, цена, сумма. Можно снять рейсы из подборки. Заполнить реквизиты исполнителя, проверить номер и дату, сохранить.
2. Счёт, строки и реестр сохраняются одной транзакцией. Данные исполнителя и заказчика, объём и цена фиксируются. В рейсах отображаются номера и даты счёта и реестра.
3. Во вкладке «УПД» выбрать счёт. Строки заполняются из сохранённого счёта, независимо от текущих фильтров дат услуг. Указать номер и дату УПД. Связи появятся у всех рейсов счёта.
4. В «Акте сверки» выбрать заказчика, при необходимости объект, и период. Начальное сальдо включает предыдущие документы и оплаты. В оборотах показываются счета и оплаты за период, включая оплаты старых счетов. Есть печать/PDF и CSV для Excel. Здесь же регистрируются частичные оплаты счетов.
5. «Зарплата» показывает сохранённые начисления по выполненным рейсам: база, премия, начислено, выплачено, остаток, налоги начисленные/оплаченные/к оплате. Выплата распределяется по начислениям одного водителя от ранних к поздним. Зарплата и налоги оплачиваются отдельно. Переплата блокируется.
6. Раздел «Зарплата и штрафы» использует тот же компонент начислений, что и бухгалтерия. Ставка 70 ₽/км фиксирована. Премии и налоги в карточке водителя действуют на будущие начисления.

## Данные и ограничения

- SQL `database/accounting-workflow.sql` дополняет действующую схему `crm_*`, не удаляя старые счета и оплаты. Это установочный SQL, не автоматически сгенерированная миграция Supabase CLI.
- Добавлены строки счетов, документы реестра/УПД и связи с рейсами; начисления и частичные выплаты зарплаты/налогов. Все новые таблицы защищены RLS по owner_id. RPC выполняются с правами вызывающего; service_role в браузере не используется.
- Завершение нового рейса фиксирует расстояние в одну сторону × 70 ₽/км и действующие премию/налоги. Изменение справочника не пересчитывает историю. Повторная обработка не создаёт дубли.
- Ранее выполненные рейсы без начислений рассчитываются явной кнопкой по текущим условиям. Исторические ставки невозможно достоверно восстановить из текущих справочников. Рейсам без водителя, даты и расстояния сначала нужно заполнить данные.
- Старые счета без строк сохранены и видны; автоматически приписывать им рейсы или создавать УПД по предполагаемым данным нельзя.
- Фильтр объекта включает целиком относящийся к нему счёт. Новые счета создаются по одному объекту. Старые счета без связи с объектом доступны при выборе «Все объекты».
- УПД сохраняется как учётный документ и печатается как проект. Юридически значимая форма с НДС, подписями и ЭДО не реализована.
- Проценты налогов сохраняют принятую в проекте модель налогов работодателя; НДФЛ отдельно не рассчитывается.
- Зарплатные остатки показаны до удержаний штрафов. Штрафы ведутся отдельно: автоматического удержания и документа погашения штрафа зарплатой пока нет. Это ограничение явно показано в интерфейсе.
- Рейсы, включённые в счёт, нельзя менять по финансовым полям или архивировать. Оплаченные начисления нельзя отменить сменой статуса рейса. Для исправления выпущенных документов понадобится отдельный процесс корректировки.
- Массовое архивирование заказчика в старом коде выполняется несколькими запросами. До публикации нужно проверить поведение с защищёнными счетами; исправление этого старого сценария в текущую перестройку не входит.

## Проверки

- `npm test`: 13 проверок прошли (9 бухгалтерия + 4 формула зарплаты).
- `npm install`: EPERM при подключении к сетевому прокси. Зависимости отсутствуют.
- `npm run lint`: `tsc: not found`; `npm run build`: `next: not found`. Типизация, Next.js и проверка в браузере не подтверждены.
- Пробный запуск SQL с ROLLBACK вернул `Invalid or expired requestState`. Успешное применение или выполнение SQL НЕ подтверждено. Миграция не публиковалась.
- Интеграционный SQL-тест подготовлен в `tests/accounting.integration.sql`, но пока НЕ выполнен. Он проверяет транзакционный счёт/реестр, УПД, защиту рейса, переплаты, повторную обработку зарплаты и RLS между двумя тестовыми пользователями. Все фикстуры откатываются.

## До GitHub и Render

1. Восстановить доступ к npm, выполнить `npm install`, сохранить lockfile. Запустить `npm test`, `npm run lint`, `npm run build`, исправить все выявленные ошибки.
2. На тестовом Supabase, соответствующем действующей схеме `crm_*`, выполнить установочный SQL. Запустить `psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f tests/accounting.integration.sql`. Провести сценарий через браузер.
3. Проверить историю старых счетов и начислений, архивирование, ограничения по налогам и форму УПД.
4. Оформить проверенные изменения отдельной веткой/PR в `novinkikinoruss-rgb/-`. Привязка этого репозитория к сайту пока установлена только по README, не через Render.
5. Перед публикацией применить проверенное дополнение схемы, затем развернуть код. Без новых таблиц бухгалтерия показывает ошибку загрузки. Рабочие данные не очищать.
6. Сохранить команды Render: сборка `npm ci && npm run build`, запуск `npm start -- -H 0.0.0.0 -p $PORT`, health check `/api/health`. Версия Node не ниже 22.18 для тестов. Проверить конфигурацию самого существующего сервиса до изменения.
