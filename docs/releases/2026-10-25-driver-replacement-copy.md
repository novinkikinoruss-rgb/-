# Замена водителя и заполнение новой заявки по номеру

В «Распределение» цветная карточка с номером открывает детали заявки; на узком экране страница прокручивается к ним. В «Машины и смены» у назначения есть «Заменить водителя». Выбор нового водителя/ФИО контрагента относится к одной машине и дате, не меняет постоянное закрепление автопарка. Для собственного водителя можно сразу отправить назначение. Новый водитель подтверждает его заново; прежний получает отменённую смену в своём кабинете и не может записать по ней факт или принять чужую замену.

Замена атомарна на сервере: проверка владельца, версии смены, текущей/будущей даты, состояния машины/водителя, пересечений; старое назначение отменяется, новое получает новый id. При неудачной отправке (например, заблокирован доступ) вся операция откатывается. Если уже были перевозки или открыт период управления прежнего водителя, замена блокируется с объяснением. История выполненной работы и выданные документы не переписываются. В «Показать отменённые назначения» доступна история; старые бланки помечены архивными и исключены из текущей печати. После замены требуется новый комплект с актуальным ФИО. Фактический рейс получает driver_id действующего назначения, даже если машина постоянно закреплена за другим водителем.

В «Создать заявку» добавлено поле «Номер предыдущей заявки» и кнопка «Заполнить по номеру». Ввод 124 или З-124 ищет среди собственных заявок, в том числе прошлых дней. Копируются заказчик/объект, маршрут и точки, часы, контакт, отправитель/получатель, наименование, масса для накладной и комментарий. Идентификатор новой заявки, выбранные даты и её автоматический новый номер не копируются. Назначения, подтверждения, фактические перевозки, документы и старые цены не переносятся; услуга/цена берутся сервером по актуальному объекту. Исходная заявка не изменяется. Неизвестный номер показывает ошибку без перезаписи формы.

## Проверки и восстановление

SQL migration 20261025134244_dispatch_replace_driver.sql уже применена к yoqejkedmksmvbqagqru. Она добавляет проверенный RPC владельца, не создаёт второй журнал рейсов/зарплаты. При восстановлении применять только отсутствующие версии к существующей совместимой схеме; не применять первоначальную dispatch-схему повторно. Старое приложение совместимо с новой функцией; для отката интерфейса не удалять таблицы, назначения, документы или рейсы.

Проверки SQL на PostgreSQL16 и рабочей схеме Supabase в транзакциях с ROLLBACK: чужой владелец и устаревшая версия; запрет замены при открытом периоде; откат при неудачной отправке; отмена прежнего назначения; сохранение старого ФИО в документах; невозможность старому водителю записать факт или принять чужую смену; фактический рейс с новым driver_id при прежнем постоянном закреплении машины; запрет замены уже выполненных перевозок; новый бланк с новым водителем; anon не может вызвать RPC. Тестовые записи не оставлены. Unit-тест копирования проверяет сохранение новых id/дат и исключение старой цены/водителя/объёма. Browser-сценарии desktop/mobile проверяют замену, историю, архивные документы, ошибочный номер, создание новой заявки по предыдущей без копирования смен.

Supabase advisor 0029 отмечает намеренно доступный authenticated SECURITY DEFINER RPC: прямые изменения таблиц запрещены, auth.uid и владелец обязательны, версия проверяется, валидация родственных сущностей делегирована существующему assign_dispatch. Публичного anon-доступа не добавлено. Справка: https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable .
