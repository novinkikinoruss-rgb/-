# Восстановление пароля по коду из письма

Пользователь запросил восстановление без вставки ссылок. На /reset-password теперь три шага: email → шестизначный код → новый пароль и подтверждение. На форме входа сохранена ссылка «Забыли пароль?». Запрос использует resetPasswordForEmail, подтверждение — verifyOtp({email, token, type:'recovery'}). Адрес фиксируется при отправке; изменение адреса очищает код. Повторная отправка ограничена 60 секундами в интерфейсе, ограничения Auth сервера остаются авторитетными. Неверный/истёкший код не открывает смену пароля, сбой отправки не выдаётся за успех, сетевые ошибки и лимит попыток не выдаются за неверный код. После сохранения запрашивается выход из сессий. Коды/пароли не записываются в журнал или исходники. Старые прямые recovery-возвраты поддержаны для совместимости; поля вставки ссылки больше нет.

## Обязательная настройка письма Supabase

Это изменение интерфейса само по себе не меняет шаблон почты у провайдера. Подключённые Supabase инструменты не предоставляют чтение/изменение Auth configuration, а Management API credential в среде не настроен. Шаблон находится в docs/templates/password-recovery-email.html. В панели проекта yoqejkedmksmvbqagqru → Authentication → Email Templates → Reset Password нужно установить тему «Код восстановления доступа к CRM» и заменить тело готовым HTML. Используется {{ .Token }}, а не {{ .ConfirmationURL }}. Не менять остальные письма, SMTP, пользователей или пароли. Прямой URL панели: https://supabase.com/dashboard/project/yoqejkedmksmvbqagqru/auth/templates . Пока шаблон не сохранён владельцем, письма продолжают приходить со старой ссылкой — выпуск не объявляется завершённой настройкой почты. После настройки запросить новый код и проверить получение в почтовом ящике, не передавая код в чат.

Альтернативный путь автоматизации при наличии безопасно настроенного SUPABASE_ACCESS_TOKEN: PATCH https://api.supabase.com/v1/projects/yoqejkedmksmvbqagqru/config/auth с mailer_subjects_recovery и mailer_templates_recovery_content. Прочитать конфигурацию до и после обновления, менять только эти поля. Токен не запрашивать в чате и не сохранять в исходниках.

## Проверки и восстановление

Production build/TypeScript, браузерные тесты desktop/mobile: запрос кода, шесть цифр, неправильный и истёкший код, привязка к email, ошибка отправки, ожидание повторной отправки, несовпадение паролей, сохранение и выход, совместимость прямого возврата. API-ответы в браузерных тестах синтетические; реальное письмо с новым кодом требует отдельной проверки после настройки шаблона. Схема БД и финансовые записи не меняются, SQL-миграций нет.

Восстановление кода: точный commit из исходного архива, npm ci, существующие настройки Render отдельно, npm test, npm run build; ветка respectlogistic/customers. При откате проверить совместимость UI и шаблона письма. Не откатывать пароль пользователя и бизнес-данные. Исходный архив исключает .env, секреты, коды, ссылки доступа, node_modules и клиентскую базу.
