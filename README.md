# respectlogistic

Новый самостоятельный проект транспортной CRM. Первый этап — раздел «Заказчики» по утверждённой концепции: светлые округлые панели, графитовое меню, лаймовые акценты, мягкий фон, анимации и адаптивный интерфейс.

## Первый раздел

- Карточка организации: ИНН с контрольной суммой, реквизиты, контакты, руководитель и банковские счета. Создание и редактирование, защита от дубликата ИНН.
- Последовательность: заказчик → договор → спецификация с услугами и ценами → объект с прорабом, контактами, маршрутом и условиями доступа.
- Несколько договоров на компанию: транспортные услуги или поставка. Автоматические номера `ТР-ГГГГ-0001` / `ПС-ГГГГ-0001`; в базе выдаются транзакционно.
- Канбан показывает фактическую полноту оформления. Перетаскивание не меняет юридические связи и пока не предусмотрено; карточка открывается нажатием.
- Папка компании с подразделами договоров, спецификаций и объектов. Генерируются HTML-проекты для скачивания и печати браузером. Это виртуальное дерево учётных документов, без загрузки подписанных файлов и без заявлений о юридической готовности шаблонов.
- Успешные действия и ошибки сопровождаются анимированными оповещениями. Успешные операции сохраняются в истории; ошибки не исчезают автоматически.
- Реальная проверка HTTP-сайта и чтения БД, статус настройки сервиса реквизитов. Наличие ключа не выдаётся за успешный ответ поставщика.

## Запуск

Node 22.18+, `npm ci`, скопировать `.env.example` в `.env.local`, `npm run dev`.

Используется тот же Supabase `yoqejkedmksmvbqagqru`, что у исходной CRM, но отдельные таблицы `respectlogistic_*`. Старые `crm_*` не изменяются, существующие заказчики не импортируются автоматически. Auth общий, браузерная сессия приложения хранится под отдельным ключом. Вход по существующему email и паролю; регистрация из интерфейса не открыта. RLS сейчас изолирует записи по пользователю; общие роли команды — следующий этап.

`database/customers.sql` — установочный SQL новой схемы, не запускать повторно после установки. Подключение к API требует только публичного publishable-ключа. Service-role ключ не используется.

Для предпросмотра дизайна оставьте обе `NEXT_PUBLIC_SUPABASE_*` переменные пустыми **до сборки**. Тогда демонстрационные данные явно помечены и хранятся только в текущем браузере; это не облачная база и не рабочие данные. Самопроизвольного переключения на демоданные при ошибке базы нет.

## Реквизиты по ИНН

Реализован серверный запрос к DaData `findById/party`. Нужен `DADATA_API_KEY` в окружении сервера (без `NEXT_PUBLIC_`); токен не отправляется в браузер. Запрос требует входа в настроенную Supabase. Без ключа форма честно сообщает о недоступности автозаполнения и разрешает ручное заполнение. Реальный ключ провайдера пока не настроен.

## Проверки

`npm test`, `npm run lint`, `npm run build`, `npx playwright install chromium`, `npm run test:e2e`. Браузерные сценарии выполняются в предпросмотре без рабочих данных; облачная транзакционность и RLS проверяются отдельным SQL-тестом с откатом. CI сохраняет реальные снимки desktop/mobile в артефакте `respectlogistic-design-and-tests`.

## Продолжение

Следующие разделы подключать по существующим идентификаторам customer/contract/specification/service/site. Рейсы, финансовые начисления, счета, выплаты и налоги создаются отдельными этапами; на этом этапе кнопки этих разделов отключены. Не переносить расчёты в компоненты интерфейса.

Отдельный репозиторий должен называться `respectlogistic`. До его создания исходники хранятся в отдельной ветке `respectlogistic/customers` существующего репозитория; эту ветку нельзя сливать в main старой CRM, поскольку это самостоятельное приложение.
